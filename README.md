# Ride-Sharing Simulation and Analytics Platform

An open-source, data-driven simulation of a ride-sharing system (like Uber/Ola), built entirely on real NCR (Delhi-NCR) booking data. It answers a practical question: **how do driver supply and rider demand levels affect service quality** (completion rate, wait times, unmet demand) — without needing access to a real ride-sharing company's live systems.

## What this project actually does, in plain terms

1. Takes a real dataset of 150,000 Uber bookings from the NCR region (2024)
2. Studies the real patterns in that data — when rides happen, how often they get cancelled, how long they take, which vehicle types are used
3. Builds a simulation that generates **synthetic** (fake but realistic) rides, calibrated to match those real patterns
4. Runs "what-if" experiments — e.g. "what happens if we had fewer drivers?" — that would be expensive or impossible to test on a real platform
5. Shows all of this through a web dashboard you can click through

## Why this is a legitimate simulation, not just noise

Every number the simulation uses (average wait time, cancellation rates, trip durations, how demand rises and falls by hour) is pulled directly from the real dataset, not invented. We then statistically test the simulation's own output against the real data (see **Validation** below) to prove it's actually reproducing real-world patterns, not just producing plausible-looking noise.

## The Dataset

**Uber Data Analytics Dashboard (NCR, 2024)** by Yashdev Laddha, via Kaggle.

Licensed under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/) — free to use and adapt, but any redistributed copy of the data (or data derived from it) must credit the original author and stay under the same license. See `DATA_LICENSE` for the full terms.

**150,000 real bookings**, one row per ride request, with columns including: date/time, booking status, vehicle type, pickup/drop location, wait time (VTAT), trip duration (CTAT), fare, distance, ratings, and cancellation reasons. It covers **NCR only** — not all of India — so all our findings are scoped to that region.

**Key real-world facts we found in this data** (via `eda.py`):

* 62% of bookings complete successfully; 18% are cancelled by the driver, 7% by the customer, 7% fail because no driver was available, 6% end incomplete
* Peak demand hour is **6 PM** (12,397 rides) — evening rush hour
* Demand is essentially flat across days of the week — no strong weekly pattern
* 7 vehicle types exist: Auto (25%), Go Mini (20%), Go Sedan (18%), Bike (15%), Premier Sedan (12%), eBike (7%), Uber XL (3%, the rarest)
* Completion rate is nearly identical across all vehicle types (~62% each) — vehicle type barely affects whether a ride succeeds

## How the Simulation Works (`src/simulation/simulate.py`)

This is the heart of the project. It uses **SimPy**, a discrete-event simulation library — meaning instead of stepping through time minute by minute, it jumps directly from one event (a ride request, a driver becoming free) to the next, which is both faster and more precise.

### The ride lifecycle, step by step

1. A **ride request** arrives (rider wants a ride)
2. The simulation tries to find a **free driver of the matching vehicle type** (an Auto request can only be matched to an Auto driver — not any random free driver). If none is free within 15 simulated minutes, the ride is marked **"No Driver Found"**
3. If a driver is found, we simulate the driver's travel time to pickup (sampled from real wait-time data) — during this the **customer might cancel**
4. If the customer doesn't cancel, the **driver might cancel** instead
5. If neither cancels, the trip happens (duration and distance sampled from real data) — it may end **"Completed"** or, rarely, **"Incomplete"**

### Two realism features worth understanding

**1. Vehicle-type-aware driver pools.** The total driver fleet is split into separate pools per vehicle type, sized proportionally to real demand (e.g. if 25% of real bookings are Auto, ~25% of simulated drivers are Auto drivers). A rider wanting a Sedan can never accidentally get matched to an Auto driver.

**2. Time-varying driver supply ("shift dynamics").** Real driver supply isn't constant all day — fewer drivers work overnight, more come online for rush hour. We model this with a `ShiftController` per vehicle-type pool: it computes, hour by hour, what fraction of that pool should be "on shift" based on that hour's real demand share, and uses lightweight background `PhantomDriver` objects to occupy the "off-shift" fleet slots — these release automatically as real demand rises, and importantly, **never interrupt a ride already in progress** (a driver finishes their current ride before effectively going off-shift).

You can toggle this with `ENABLE_SHIFT_DYNAMICS = True/False` and tune how aggressive the day/night swing is with `MIN_ACTIVE_FRACTION` (0.5 = at the quietest hour, half the fleet is still working), both at the top of `simulate.py`.

### Known limitation, honestly stated

Uber XL (3% of real demand) gets very few dedicated drivers under this type-segmented model, making it structurally hard to serve reliably — a real, well-documented trade-off in queueing theory called the *resource pooling effect* (splitting one shared resource into narrow specialized pools loses efficiency). Worth mentioning in your report as a considered limitation, not an oversight.

## Validation — proving the simulation is realistic (`src/analytics/metrics.py`)

Two layers of validation:

1. **Visual comparison** — a bar chart (`sim_vs_real_outcomes.png`) placing the simulation's outcome percentages next to the real dataset's, side by side.
2. **Statistical test (Kolmogorov-Smirnov)** — a formal test comparing the simulated distributions of wait time, trip duration, and trip distance against the real data's distributions. Produces a "D statistic" (0 = identical distributions) for each. D < 0.1 is read as a strong match.

   > **Caveat:** With large sample sizes this test's p-value is often "significant" even for near-identical distributions — judge fit by the D statistic, not the p-value alone.

## Scenario Analysis (`src/scenarios/what_if.py`)

Runs the simulation under 5 predefined driver-supply/demand combinations (baseline, low supply, high supply, +30% demand, -30% demand) and compares their KPIs side by side — this answers "what would happen if..." questions that would be risky or impossible to test on a live platform.

## The Dashboard (`app.py` + `templates/` + `static/`)

A Flask web app that wraps everything above in a browser UI:

* Sliders to adjust driver count and demand, a **Run Simulation** button
* Live KPI cards (completion rate, no-driver-found %, utilization, wait time)
* Charts: outcome breakdown, requests by hour
* A **Run Scenario Comparison** button showing all 5 what-if scenarios at once
* A sample of the generated synthetic ride data, downloadable as CSV

## How to Run This

### First-time setup

```bash
pip install -r requirements.txt
```

Download the dataset from [Kaggle](https://www.kaggle.com/datasets/yashdevladdha/uber-ride-analytics-dashboard) and place the CSV in `data/raw/`.

### Run the full analysis pipeline (preprocessing -> EDA -> simulation -> scenarios)

```bash
python main.py
```

Outputs land in `outputs/figures/` and `outputs/reports/`.

### Run the interactive dashboard

```bash
python app.py
```

Then open **http://localhost:5000** in a browser.

### Re-tune the driver count (if you change the dataset or simulation logic)

```bash
python tune_drivers_v2.py
```

## Configuration Reference (top of `src/simulation/simulate.py`)

| Setting                   | What it controls                                                  |
| ------------------------- | ----------------------------------------------------------------- |
| `NUM_DRIVERS`             | Total fleet size, split across vehicle types                      |
| `MAX_WAIT_FOR_DRIVER_MIN` | How long a request waits before "No Driver Found"                 |
| `ENABLE_SHIFT_DYNAMICS`   | Whether driver supply varies by hour (True) or stays flat (False) |
| `MIN_ACTIVE_FRACTION`     | At the quietest hour, what fraction of the fleet still works      |
| `RANDOM_SEED`             | Fixed seed so results are reproducible run to run                 |
